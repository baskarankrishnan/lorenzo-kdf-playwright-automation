## 📝 Code Patterns & Conventions

### Function Return Type
```typescript
interface Outcome {
  code: 0 | 1;        // 0 = success, 1 = failure
  value?: string;     // Result/error message
}
```

### Test Step Interface
```typescript
interface testStep {
  actionType: string;        // 'CLICK', 'TYPE', 'VERIFY', etc.
  elementType?: string;      // 'BUTTON', 'TEXTBOX', 'LABEL', etc.
  locator?: string;          // Element selector/locator
  page?: string;             // Page object name
  element?: string;          // Element name from page
  testData?: string;         // Input data (supports #{variables})
  expectedResult?: string;   // Expected result for assertions
  property?: string;         // Property for assertions
  value?: string;            // Value for assertions
  description?: string;      // Step description
  timeOut?: number;          // Timeout in milliseconds
  isDDT?: boolean;           // Data-driven test flag
}
```

### Typical Function Structure
```typescript
/**
 * Function description with @param, @returns, @example
 * @param page - Playwright Page
 * @param testStep - Test step configuration
 * @returns Outcome with code and value
 */
export async function functionName(page: Page, testStep: testStep): Promise<Outcome> {
  try {
    // Resolve variables and locators
    const locatorString = getLocatorString(testStep);
    const resolvedData = resolveTestVariables(testStep.testData);
    
    // Perform action
    const element = await resolveElement(page, locatorString, testStep);
    await element.click();
    
    // Log success with emoji
    console.log('✅ Action completed');
    return { code: 0, value: 'Success message' };
  } catch (error) {
    // Log error with emoji
    console.error('❌ Action failed: ' + error);
    return { code: 1, value: error.message };
  }
}
```

### Variable Resolution
- All test data uses `resolveTestVariables()` for dynamic substitution
- Syntax: `#{variableName}` in test data
- Variables sourced from: Excel, database, runtime execution
- Built-in variables: `_currentDate`, `_currentTime`, `_randomNumber`, `_uuid`, etc.

### Locator Resolution
- Formats: CSS selectors, XPath, role-based locators, Playwright Locators
- Syntax: `[LOCATOR_TYPE]:[locator_value]`
- Examples: `CSS:.button-submit`, `XPath://button[@type='submit']`, `role=button`
- Supports variable substitution in locators

### Error Handling
- All functions wrapped in try-catch
- Errors logged with emoji indicators (✅ success, ❌ error, ⚠️ warning, ℹ️ info)
- Consistent Outcome return type for all functions
- Never throw exceptions - always return Outcome

### Logging Pattern
```typescript

console.warn('⚠️ Warning message');        // Warning
console.log('ℹ️ Info message');            // Info
```

## ✅ Best Practices

### When Adding New Functions
1. Add complete JSDoc with @param, @returns, @example tags
2. Use consistent try-catch error handling
3. Return Outcome type `{code: 0/1, value: string}`
4. Log with emoji indicators (✅, ❌, ⚠️, ℹ️)
5. Use `resolveTestVariables()` for data substitution
6. Use `resolveElement()` for element finding
7. Add to appropriate file:
   - Element interactions → elementActions.ts
   - Browser control → browserActions.ts
   - Verifications → assertActions.ts
   - Data handling → dataActions.ts
   - Utilities → utilities/ folder

### When Creating Page Objects
1. Register in `product/pageRegistry.ts`
2. Export locator objects with clear names
3. Use consistent CSS selector or XPath format
4. Group related locators in logical sections
5. Document complex locators with comments
6. Include page title and URL patterns for dynamic lookup
7. Support multiple selector alternatives

### When Writing Tests
1. Use test case Excel files for data
2. Support data-driven execution (multiple rows)
3. Capture evidence (screenshots) on failure
4. Log all step execution with descriptive messages
5. Use database for result storage and tracking
6. Follow Outcome return type convention
7. Use resolveTestVariables for dynamic data
8. Validate page state before interactions

### Variable Naming Conventions
- Test data: Use camelCase (`userName`, `patientId`)
- Excel columns: Use PascalCase (`PatientName`, `ReferralDate`)
- Locators: Use descriptive names (`btn_Submit`, `txt_Username`)
- Functions: Use verbActionSubject pattern (`clickElement`, `waitForRoller`)
- Constants: Use UPPER_SNAKE_CASE (`MAX_TIMEOUT`, `DEFAULT_DELAY`)
- Classes: Use PascalCase (`BrowserFocusTracker`, `VariableManager`)

### Element Repository Structure
**Location:** `kdf-generation/kdf-samples/ElementRepository_Lorenzo_3.json` (2227 elements)

```json

  "page": "pageHome",
```

## 📝 Code Patterns & Conventions

### Function Return Type
```typescript
interface Outcome {
  code: 0 | 1;        // 0 = success, 1 = failure
  value?: string;     // Result/error message
}
```

### Typical Function Structure
```typescript
/**
 * Function description
 * @param page - Playwright Page
 * @param testStep - Test step configuration
 * @returns Outcome with code and value
 * @example
 * outcome = await clickElement(page, { 
 *   locator: '#buttonId',
 *   description: 'Click submit'
 * });
 */
export async function clickElement(
  page: Page,
  testStep: testStep
): Promise<Outcome> {
  try {
    const locatorString = getLocatorString(testStep);
    const element = await resolveElement(page, locatorString);
    await element.click();
    logger.log('✅ Element clicked');
    return { code: 0, value: 'Clicked successfully' };
  } catch (error) {
    logger.error('❌ Click failed: ' + error);
    return { code: 1, value: error.message };
  }
}
```

### Variable Resolution
- All test data uses `resolveTestVariables()` for dynamic substitution
- Syntax: `#{variableName}` in test data
- Variables sourced from: Excel, database, runtime execution

### Locator Resolution
- Formats: CSS selectors, XPath, role-based locators
- Syntax: `[LOCATOR_TYPE]:[locator_value]`
- Examples: `CSS:.button-submit`, `XPath://button[@type='submit']`

### Error Handling
- All functions wrapped in try-catch
- Errors logged with emoji indicators (✅ success, ❌ error)
- Consistent Outcome return type for all functions

### Logging Pattern
```typescript
// Success: ✅ message
// Error: ❌ message
// Info: ℹ️ message
// Warning: ⚠️ message
logger.log('✅ Action completed');
logger.error('❌ Action failed');
```
